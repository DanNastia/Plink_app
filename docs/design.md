# A-03 · Интерфейс Plink

Ответственная участница — Анастасия Данилова. Проект экрана для разработчика. Основа — [требования](requirements.md) и [архитектура](architecture.md). В исходной ветке feature/frontend компонент App показывает демонстрационный счётчик Vite. Ниже описан будущий экран.

## Главный экран

Студент открывает Plink перед покупкой. Первый ответ на экране — сколько рублей доступно в день до следующего поступления. Второй — какая часть текущего остатка уже нужна для платежей.

| Ряд на широком экране | Левая часть | Правая часть |
|---|---|---|
| Верх страницы | Заголовок «Plink» | Поле «Следующее поступление» и кнопка «Сохранить дату» |
| Сводка на всю ширину | Крупно «Доступно в день», сумма и число оставшихся дней | «Остаток», «На обязательные платежи», «Свободно до поступления». При нехватке — строка «Не хватает» с суммой |
| Ввод | «Добавить операцию» | «Обязательные платежи» с формой и списком |
| Планирование и анализ | «Проверить покупку» | «Расходы за месяц» с названием месяца |
| Низ страницы | Журнал операций на всю ширину | |

Дату выбирают в календарном поле и сохраняют. После успешной записи рядом появляется дата, сводка и прогноз получают новый период. Сам доход вводится отдельно. В полночь и при возврате во вкладку показатели должны соответствовать сегодняшней местной дате. Рубли показываются с разрядами и знаком ₽, копейки сохраняют точность до двух знаков.

## Действия пользователя

**Записать операцию.** В одной форме выбрать «Расход» или «Доход». Поля по порядку: «Сумма, ₽», «Категория», «Дата» (по умолчанию сегодня), «Комментарий» (необязательно). Переключение типа обновляет список категорий и снимает несовместимый выбор. Для первого дохода можно выбрать «Начальный остаток». Кнопка называется «Добавить расход» или «Добавить доход». После успешной записи показать сообщение, очистить черновик, обновить сводку и журнал. В журнале новые по дате операции сверху. Каждая запись показывает дату, тип, категорию, сумму со знаком и комментарий при наличии.

**Запланировать платёж.** В разделе обязательств выбрать «Добавить платёж», заполнить название, сумму, расходную категорию и срок, нажать «Сохранить платёж». Показать строку с этими данными и статусом. До оплаты доступны «Оплатить» и «Отменить план». После оплаты статус — «Оплачено», действия убраны, в журнале один расход сегодняшней датой. Повторное нажатие не создаёт вторую операцию. После отмены неоплаченный план исчезает, резерв пересчитывается. При действующем периоде подписывать принадлежность неоплаченного платежа: «В резерве» для срока до поступления, «На следующий период» для срока в день поступления и позже. Для пропущенного срока дополнительно показать «Просрочен».

**Проверить покупку сегодня.** Открыть «Проверить покупку», ввести «Стоимость покупки, ₽». При корректной стоимости показать две группы — «Сейчас» и «После покупки», в каждой дневной лимит и дефицит. Например, 10 мая при остатке 900 ₽, резерве 300 ₽ и поступлении 13 мая лимит составляет 200 ₽. Для покупки за 150 ₽ показать 150 ₽ в день после покупки, дефицит в обеих группах 0 ₽. Для покупки за 650 ₽ показать 0 ₽ в день и дефицит 50 ₽. Изменение суммы обновляет сравнение. «Закрыть» сбрасывает черновик. Баланс, платежи, диаграмма и журнал остаются прежними.

**Посмотреть структуру расходов.** За текущий календарный месяц вывести горизонтальные полосы Recharts по категориям фактически проведённых расходов. Рядом с каждой полосой постоянно видны название, сумма и доля месячных расходов. Цвет и наведение не требуются для чтения. Платёж появляется в диаграмме после оплаты. Для одной категории показать полную полосу и 100%.

## Состояния и обратная связь

| Условие | Что видит пользователь и как продолжить |
|---|---|
| Первый запуск | Остаток 0 ₽. «Операций пока нет» и подсказка внести начальный остаток через «Доход». «Обязательных платежей пока нет» рядом с кнопкой добавления |
| Нет будущей даты, наступил или прошёл день дохода | «Укажите будущую дату поступления» рядом с календарём. Показать баланс и платежи. Для показателей периода — прочерк, прогноз недоступен до сохранения новой даты |
| Свободно ровно 0 ₽ | При действующем периоде лимит 0 ₽, дефицит 0 ₽. Можно добавить операцию или проверить покупку |
| Средств недостаточно | Сохранить знак отрицательного остатка или свободной суммы. Лимит 0 ₽. Текст «Не хватает … ₽» содержит точное значение дефицита |
| Нет расходов в месяце | Вместо диаграммы «В этом месяце расходов пока нет» |
| Неверная сумма, включая пустую, ноль или лишние копейки | Под полем «Введите положительную сумму, например 12,34». Для слишком большой суммы — «Сумма слишком велика». При ошибке прогноза убрать старое сравнение |
| Пустое обязательное поле, неверная дата или категория | Указать конкретное исправление, например «Выберите категорию расхода», «Введите название» или «Дата операции не может быть в будущем». Сохранить введённое, перевести фокус на первое ошибочное поле |
| LocalStorage недоступен для записи | Рядом с действием «Не удалось сохранить изменения» и доступная причина. Оставить форму заполненной для повтора, показывать последние сохранённые итоги |
| Ошибка чтения или повреждены данные | Вверху «Не удалось прочитать сохранённые данные». Заблокировать запись и скрыть неподтверждённые значения. Исключить автоматическую очистку |

## Экран шириной 360 px

Поля страницы по 16 px оставляют 328 px под одну колонку. Порядок чтения и фокуса: дата → дневной лимит и детали сводки → операция → платежи → прогноз → диаграмма → журнал. Подпись поля стоит над вводом. Дата и её кнопка, действия платежа и группы сравнения располагаются друг под другом. Каждое действие доступно с клавиатуры, фокус заметен, текст ошибки связан со своим полем.

Для строки журнала сначала вывести категорию и дату, затем сумму и комментарий. Длинные названия и крупные суммы могут занять отдельную строку. Диаграмма занимает ширину контейнера, текст категории и чисел расположен над полосой. Проверить при реализации без горизонтальной прокрутки три случая: длинное название ЖКХ с кнопками оплаты, стоимость с копейками и ошибкой ввода, сравнение при дефиците после покупки.

## Компоненты и входные данные

App читает сохранённые данные, передаёт события на запись и получает расчёты из финансового модуля. Имена ниже предложены для реализации. Суммы между компонентами передаются в копейках, даты — календарными строками. Ошибки записи доступны форме, инициировавшей действие.

| Дочерний компонент App | Входные данные | События и локальное состояние |
|---|---|---|
| BudgetSummary | Сегодня, nextIncomeDate, баланс, резерв, свободная сумма, дни, лимит, дефицит либо признак отсутствия периода | Черновик даты, onSaveDate(date) |
| TransactionForm | Сегодня, категории с типом, состояние записи | Черновик полей, onAddTransaction(поля) |
| Obligations | obligations, расходные категории, сегодня, дата поступления, состояние записи | Черновик плана, onAdd(поля), onPay(id), onCancel(id) |
| PurchaseForecast | Доступность периода, текущие лимит и дефицит, функция прогноза из финансового модуля | Хранит введённую цену и состояние открытия. Вызывает прогноз для суммы, обработчик записи отсутствует |
| ExpenseChart | Текущий месяц, строки с категорией, суммой и долей | Отображает данные Recharts и текстовые подписи |
| TransactionList | transactions и справочник категорий | Отображает записи и пустое состояние |

## Передача разработчику

Сверить интерфейс с пятью проверками ТЗ. Особенно важен переход после оплаты из примера выше: остаток меняется с 900 ₽ на 600 ₽, резерв с 300 ₽ на 0 ₽, дневной лимит остаётся 200 ₽. После перезагрузки видны запись оплаты и её статус. Это ожидаемые результаты для реализации. Авторам предлагается согласовать визуальный выбор горизонтальных полос и порядок блоков мобильного экрана.

## A-04 · Проект контракта React и финансового ядра

Ответственная — Анастасия Данилова. Статус — предложение для совместного согласования с Марией. Основания: требования и архитектура из main на d97fd44, дизайн из feature/frontend на 7540a0b. Четыре экспорта уже есть в [finance.js](https://github.com/DanNastia/Plink_app/blob/d97fd44/app/src/finance.js). Бюджет и прогноз сверены с [budget-rules.js в ветке Марии](https://github.com/DanNastia/Plink_app/blob/f6a2b6a/app/src/budget-rules.js). Предлагаем App использовать finance.js как точку импорта. Мария может реэкспортировать два готовых расчёта после согласования. Такое подключение сохраняет единственную реализацию каждого расчёта.

### Типы на границе модулей

- Деньги — number, безопасное целое в копейках. Ввод пользователя — строка в рублях. Календарная дата — строка YYYY-MM-DD, today — местный день, переданный App.
- Transaction — объект с полями id, categoryId, date, comment (строки), type ('income' или 'expense') и amountKop (положительные копейки).
- Obligation — id, title, categoryId, dueDate (строки), amountKop (положительные копейки), paidTransactionId (строка или null). App передаёт явный null для неоплаченного плана. При загрузке storage.js проверяет ссылки и структуру до расчётов.
- BudgetInput — объект {balanceKop: number, obligations: Obligation[], today: string, nextIncomeDate: string | null}. Баланс может быть отрицательным.
- Budget — один из трёх результатов Марии. При status='available' содержит days (целое > 0), reserveKop, freeKop, deficitKop, dailyLimitKop (числа). При status='incomeDueToday' те же поля, days=0 и dailyLimitKop=null. При status='unavailable' объект содержит только status. Для обоих последних статусов интерфейс показывает просьбу выбрать будущую дату, скрывает все показатели периода и отключает прогноз. Баланс, журнал, платежи и диаграмма остаются доступны.

### Вызовы и ошибки

Во всех строках вызов выполняет App или переданный им обработчик. Дочерний компонент получает результат через props. Имена первых шести функций и их результаты соответствуют указанным исходникам.

| Функция | Входные аргументы | Возвращаемое значение | Ошибки и ограничения | Потребитель |
|---|---|---|---|---|
| parseAmountKop | input: string, например «12,34» | number, например 1234 | TypeError при неверном формате, знаке или лишних дробных цифрах. RangeError при нуле или выходе за безопасный диапазон | TransactionForm, Obligations, PurchaseForecast через обработчики App |
| sumIncomeKop | transactions: Transaction[] | number, сумма доходов, для пустого массива 0 | TypeError при неизвестном type. RangeError при некорректной сумме дохода или переполнении его итога | App косвенно через calculateBalanceKop для BudgetSummary |
| sumExpenseKop | transactions: Transaction[] | number, сумма расходов, для пустого массива 0 | TypeError при неизвестном type. RangeError при некорректной сумме расхода или переполнении его итога | App косвенно через calculateBalanceKop для BudgetSummary |
| calculateBalanceKop | transactions: Transaction[] | number, остаток со знаком, для пустого массива 0 | Передаёт ошибки двух функций суммирования | App для BudgetSummary и входа бюджета |
| calculateBudget | input: BudgetInput | Budget | TypeError при неверном формате проверяемой даты, RangeError при несуществующей дате, недопустимой сумме или переполнении. Отсутствие будущего периода выражено статусом | BudgetSummary, PurchaseForecast через App |
| forecastPurchase | input: BudgetInput, purchaseKop: number > 0, obligationId?: string | При доступном периоде {status:'available', before: Budget, after: Budget}; иначе исходный Budget | Ошибки бюджета. В доступном периоде RangeError при неверной цене, переполнении, неизвестном id плана либо цене выше его неоплаченной части. При недоступном периоде возврат до проверки цены | PurchaseForecast через обработчик App. Для дополнительной покупки третий аргумент опускается |
| summarizeMonthlyExpenses (предложение) | transactions: Transaction[], today: string | Массив {categoryId: string, amountKop: number, percent: number}. percent в шкале 0–100. Пустой месяц даёт [] | Предлагаются TypeError при неверном типе или формате, RangeError при невозможной дате, небезопасной сумме или итоге | App для ExpenseChart. Название категории подставляется из справочника |

При проверке формы App передаёт исходную строку в parseAmountKop один раз. Ошибка возвращается форме для показа рядом с полем, черновик сохраняется. Для прогноза App передаёт полученные копейки и текущий BudgetInput в forecastPurchase. Форма получает before и after либо признак недоступности. Для сохранения операции App проверяет кандидат нового состояния, включая допустимость итогов, записывает его через storage.js и только после успеха обновляет экран. При ошибке чтения сохраняет исходную запись и блокирует перезапись.

### Состояние и props

| Где находятся данные | Содержимое и передача |
|---|---|
| Сохраняемое состояние App | Только transactions, obligations, nextIncomeDate в plink.v1. При оплате App связывает ровно один расход с планом и записывает оба изменения вместе. Повторная команда по уже оплаченному id ничего не добавляет |
| Состояние текущего сеанса | App отслеживает today и ошибки чтения/записи. В полночь и при возврате фокуса обновляет today. В формах локально живут ввод, выбранная категория, черновик даты или цены и состояние открытия |
| Вычисляемые при показе | Баланс, бюджет, сравнение покупки и строки диаграммы. App получает их из ядра. React отвечает за формат рублей, подписи и доступность действий |
| Props сводки и форм | BudgetSummary получает баланс, Budget, дату и onSaveDate. TransactionForm получает today, категории, ошибку и onAddTransaction. Obligations получает планы, today, дату поступления, категории, ошибку и onAdd/onPay/onCancel |
| Props прогноза, диаграммы и журнала | PurchaseForecast получает статус периода и onForecast(rawPrice: string); обработчик возвращает результат прогноза или ошибку поля. ExpenseChart получает месяц и подписанные строки агрегата. TransactionList получает операции и справочник |

### Демонстрационный набор для параллельной разработки

Отдать компонентам следующие статические данные через те же props. Временный обработчик прогноза для демонстрации выбирает заранее записанный ответ для указанного примера. Набор используется только в локальном сеансе разработки, без записи в plink.v1.

```json
{
  "today": "2026-05-10",
  "nextIncomeDate": "2026-05-13",
  "transactions": [
    {"id":"t1","type":"income","date":"2026-05-10","categoryId":"stipend","amountKop":100000,"comment":""},
    {"id":"t2","type":"expense","date":"2026-05-10","categoryId":"food","amountKop":10000,"comment":""}
  ],
  "obligations": [
    {"id":"p1","title":"ЖКХ","categoryId":"home","dueDate":"2026-05-12","amountKop":30000,"paidTransactionId":null}
  ]
}
```

Демонстрационные подписи категорий: stipend — «Стипендия», food — «Продукты», home — «ЖКХ». Для сводки передать balanceKop=90000 и before из примера ниже. В диаграмме одна строка food, 10000 копеек, 100%. При вводе «150,00» ожидаемый ответ обработчика:

```json
{
  "status":"available",
  "before":{"status":"available","days":3,"reserveKop":30000,"freeKop":60000,"deficitKop":0,"dailyLimitKop":20000},
  "after":{"status":"available","days":3,"reserveKop":30000,"freeKop":45000,"deficitKop":0,"dailyLimitKop":15000}
}
```

Другие состояния для вёрстки: при пустых массивах и nextIncomeDate=null баланс 0, бюджет {status:'unavailable'}, строки диаграммы пусты. При вводе «1,234» показать ошибку поля и убрать прежний прогноз. При открытии того же набора 13 мая показать сохранённый баланс 900 ₽ и предложение обновить дату. Оплата p1 целиком переводит баланс в 60000, резерв в 0, лимит остаётся 20000. После перезагрузки ссылка плана ведёт к той же расходной операции.

### К совместному согласованию

1. Подтвердить точку импорта и предложенное имя и результат функции для диаграммы. До согласования демонстрационный экран использует статические строки.
2. Подтвердить отображение incomeDueToday как недоступного периода. В ветке Марии ядро в этот день ещё возвращает резерв и свободную сумму; ТЗ требует скрывать их.
3. В ветке Марии есть необязательные paidAmountKop, dueBeforeIncome и прогноз оплаты по obligationId. Для согласованного MVP предлагаем использовать полную оплату через paidTransactionId, правило срока из ТЗ и прогноз только дополнительной покупки. Расширение схемы хранения и новые действия требуют отдельного решения обеих участниц.
