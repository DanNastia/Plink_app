# M-17 · Хранилище Plink

Модуль `app/src/storage.js` хранит полное состояние в JSON под ключом `plink.v1`. Схема операций, обязательств и даты поступления определена в [архитектуре](architecture.md).

Справочник передаёт вызывающий код. Используйте существующий объект `categories` из `App.jsx` с двумя массивами `income` и `expense`. Каждый элемент — пара `[id, название]`. Тот же объект используют формы. Передавайте одинаковые идентификаторы при загрузке и записи, включая категории ранее сохранённых операций.

## Публичные функции

| Вызов | Результат | Ошибки |
|---|---|---|
| `createInitialState()` | Новый объект `{ transactions: [], obligations: [], nextIncomeDate: null }` с независимыми массивами | Входных параметров нет |
| `validateState(state, categories)` | `undefined`, если структура, суммы, даты, категории и ссылки оплаты допустимы | `TypeError` при неверном типе, формате, категории, идентификаторе или ссылке. `RangeError` при невозможной дате, неверной сумме или переполнении итогов операций |
| `loadState(categories, storage?)` | Восстановленное состояние. Если ключ отсутствует, возвращает новое пустое состояние | `read_failed` при отказе чтения, `invalid_saved_state` при повреждённом JSON или невалидных данных |
| `saveState(state, categories, storage?)` | `undefined` после успешного `setItem` | Ошибки чтения и валидации сохранения, ошибки проверки нового состояния, `write_failed` при отказе сериализации или записи |

В браузере `storage` по умолчанию берётся из `globalThis.localStorage`. Тесты могут передать объект с методами `getItem(key)` и `setItem(key, value)`. Ошибки хранилища имеют поле `code` и исходную причину в `cause`. Отсутствие ключа установлено только тогда, когда `getItem` вернул `null`.

`saveState` читает и проверяет текущую запись при каждой попытке. Повреждённый JSON, неверная структура или невалидная ссылка оплаты блокируют запись, исходное значение сохраняется. При корректной текущей записи модуль проверяет новый объект и одним вызовом `setItem` передаёт сериализованное состояние. Так расход и ссылка оплаты сохраняются вместе. Сравнение версий между вкладками не предусмотрено. Архитектура рассчитана на одну активную вкладку.

Хранилище проверяет существование календарных дат. Прошедшая или наступившая дата поступления допустима. Проверку даты новой операции относительно сегодняшнего дня выполняет App при вводе. Для неоплаченного обязательства передаётся явный `null`. Ссылка оплаченного обязательства ведёт к единственному фактическому расходу с той же суммой и категорией.

## Подключение в App

```js
import { createInitialState, loadState, saveState, validateState } from './storage.js'

// categories — существующий справочник App.
const empty = createInitialState()
validateState(empty, categories)

function readInitialState() {
  try {
    return { state: loadState(categories), readError: null }
  } catch (readError) {
    return { state: null, readError }
  }
}

function persistState(nextState) {
  try {
    saveState(nextState, categories)
  } catch (error) {
    return error
  }
  setState(nextState)
  return null
}
```

Вызовите `readInitialState` при инициализации. При ошибке чтения покажите сообщение и заблокируйте действия записи. После ошибки в `persistState` сохраните последнее успешное состояние и черновик формы. При оплате App проверяет, что план ещё не оплачен, формирует единый объект с новым расходом и обновлённым планом, затем вызывает `persistState` один раз. Очистите форму после успешного сохранения.

## Проверка

Из каталога `app/` выполните `node --test src/storage.test.js`. При интеграции в App отдельно проверьте оплату, повторную команду оплаты и перезагрузку в тестовом профиле браузера. При отказе записи предыдущий журнал и состояние плана должны сохраниться, а пользователь должен иметь возможность повторить действие.
