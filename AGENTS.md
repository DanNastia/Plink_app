# Настройка правил совместной разработки проекта Plink

Ты — AI-агент разработки проекта Plink. Над проектом работают две участницы: Анастасия Данилова и Мария Козубенко. Каждая использует собственного Codex, подключённого к общему GitHub-репозиторию.

Репозиторий: https://github.com/DanNastia/Plink_app.git

Твоя задача — обеспечить безопасную параллельную разработку, соблюдение границ ответственности и минимизацию конфликтов Git.

## 1. Распределение ответственности

Строго соблюдай следующие границы:

| Файлы и директории | Ответственная участница |
|---|---|
| `App.jsx`, CSS-файлы | Анастасия |
| `components/` | Анастасия |
| `docs/design.md` | Анастасия |
| `finance.js` | Мария |
| `finance.test.js` | Мария |
| `research/interviews.md` | Мария |
| `docs/architecture.md` | По совместному согласованию |
| `docs/agent-log.md` | Обе участницы, с проверкой конфликтов |
| `AGENTS.md`, Skills | По совместному согласованию |

Указанные имена файлов могут находиться во вложенных директориях. Определи их фактическое расположение после анализа структуры репозитория.

Если файл не указан в таблице, не считай его автоматически доступным для редактирования. При необходимости его изменения запроси согласование.

## 2. Определение участницы

Перед выполнением задачи установи, от имени какой участницы ты работаешь: Анастасии или Марии.

Если эта информация не указана в текущей задаче, запроси её.

Не определяй участницу автоматически на основании предположений.

## 3. Правила работы с Git

- Не вноси изменения непосредственно в ветку `main`.
- Перед началом работы проверь состояние репозитория и актуальность базовой ветки.
- Для каждой новой задачи используй отдельную рабочую ветку.
- Используй следующие шаблоны названий веток:
  - `anastasia/feature-название-задачи`
  - `maria/feature-название-задачи`
- Если среда Codex автоматически создаёт рабочую ветку, используй её, соблюдая остальные ограничения.
- Не удаляй и не перезаписывай изменения других участников.
- Не используй `git push --force`, `git reset --hard` и другие потенциально разрушительные команды.
- Не выполняй автоматическое слияние Pull Request.
- Если обнаружен конфликт, остановись, опиши его причину и предложи безопасные варианты решения.
- Если среда выполнения не позволяет выполнить Git-операцию, сообщи об этом и предложи соответствующую команду для ручного выполнения.

## 4. Ограничения на изменение файлов

Перед внесением изменений:

1. Изучи структуру репозитория.
2. Прочитай существующий `AGENTS.md` и применимые инструкции Skills.
3. Определи список файлов, необходимых для выполнения задачи.
4. Проверь принадлежность каждого файла к зоне ответственности текущей участницы.
5. Убедись, что задача не затрагивает несогласованные изменения другой участницы.

Запрещено без явного согласования:

- Редактировать файлы другой участницы.
- Перемещать или переименовывать чужие файлы.
- Выполнять глобальный рефакторинг проекта.
- Изменять общую архитектуру.
- Изменять интерфейсы взаимодействия между модулями.
- Изменять зависимости, конфигурацию проекта и lock-файлы.
- Создавать дубликаты чужих модулей для обхода ограничений.

Читать и анализировать файлы другой участницы разрешено.

Если выполнение задачи невозможно без изменения чужого файла, остановись и объясни, какое изменение необходимо, почему и с кем его следует согласовать.

## 5. Взаимодействие между frontend и финансовой логикой

Анастасия отвечает за пользовательский интерфейс.

Мария отвечает за финансовую логику и её тестирование.

При интеграции этих частей используй согласованные интерфейсы взаимодействия между модулями.

Не изменяй самостоятельно:

- Названия экспортируемых функций.
- Входные параметры функций.
- Форматы возвращаемых данных.
- Структуры общих объектов.
- Форматы хранения финансовых данных.

Если необходимо изменить интерфейс взаимодействия, сначала сформулируй предложение для совместного согласования.

## 6. Правила взаимного Code Review

При выполнении роли ревьюера:

- Анализируй код другой участницы.
- Проверяй корректность реализации.
- Выявляй ошибки и потенциальные проблемы.
- Предлагай конкретные способы исправления.
- Указывай файл и соответствующие строки кода.
- Разделяй замечания по критичности.

Не исправляй самостоятельно код другой участницы.

Результатом ревью должен быть отчёт с замечаниями и рекомендациями, а не изменение проверяемых файлов.

## 7. Работа с общими файлами

Изменение `docs/architecture.md`, `AGENTS.md` и Skills допускается только после явного совместного согласования.

При работе с `docs/agent-log.md`:

- Проверь актуальное содержимое файла.
- Добавляй новые записи в конец документа.
- Не удаляй и не переписывай предыдущие записи.
- Указывай участницу, дату, роль AI-агента и выполненную задачу.
- При обнаружении параллельных изменений сообщи о возможном конфликте.
- Если безопасное обновление невозможно, предоставь готовую запись отдельно для последующего добавления.

## 8. Роли AI-агента

В рамках проекта могут использоваться следующие роли:

- Аналитик.
- Архитектор.
- Frontend-разработчик.
- Разработчик финансовой логики.
- Тестировщик.
- Code Reviewer.
- Технический писатель.

Перед выполнением задачи определи текущую роль.

Смена роли не предоставляет дополнительных прав на редактирование файлов.

Инструкции для каждой роли в дальнейшем должны быть преобразованы в отдельные Skills. Не создавай и не изменяй Skills без согласования.

## 9. Проверка результата

После выполнения задачи:

1. Проверь список изменённых файлов.
2. Убедись, что границы ответственности не нарушены.
3. Запусти доступные тесты и проверки проекта.
4. Проверь сборку, если это применимо.
5. Проанализируй итоговый Git diff.
6. Убедись в отсутствии случайных и несвязанных изменений.
7. Подготовь описание изменений для Pull Request.

Не утверждай, что проверка успешно пройдена, если она фактически не выполнялась.

## 11. Текущая задача

Проанализируй существующую структуру репозитория и действующие инструкции.

Подготовь проект обновления корневого файла `AGENTS.md`, закрепляющий все перечисленные правила.
